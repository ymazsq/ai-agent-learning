## 1. 目标与边界

两条方向并行，共用同一条主线项目：

| 方向 | 要求 | 本计划的覆盖方式 |
|---|---|---|
| A. AI 全栈开发工程师 | Node 服务、HTTP/SSE、数据库、流式 UI、部署 | 模块三（后端）、模块六（流式 UI 与部署） |
| B. Agent 应用开发工程师 | 面向业务场景的 Agent：工具设计、检索、多 Agent、评测、权限 | 模块二（RAG）、模块四（工具与多 Agent）、模块五（评测与安全） |

**个人背景与由此做出的取舍**（约 10 年前端工程经验）：
- 通用前端与工程化不再单列课程。流式渲染、状态同步、性能和埋点这些经验直接复用，学习重点放在 Agent 相关的 UI（工具调用过程、写操作确认）。
- 后端没有 Node 服务经验，模块三不压缩，并在模块三开头补一天 HTTP 与服务端基础（见下表）。
- 面试重点是架构决策、成本与权限、团队落地。因此模块七单独做系统设计训练，并把前端经验映射成 Agent 产品侧的经验。

边界：
- 业务场景只用个人学习数据或虚构数据。**不使用、不复制公司的代码、文档或数据**。
- 不做模型训练。Python 只做模块七（面试冲刺）的阅读和小改动，不做系统开发。
- 包管理用 pnpm；语言用 TypeScript。
- 先手写、再用框架：每个主题先在当前代码上复现问题（"撞墙"），再接 SDK 或框架。这是设计文档的原则，本计划保留。

学习节奏：没有固定截止日期。时间多时一次可以学 1–2 个 Day；时间少时一个 Day 可以拆成几天。缺课的处理见第 4 节"补课规则"。

## 2. 毕业作品

**个人知识助手（Agent + 全栈）**：一个 Web 应用，用户上传自己的笔记，Agent 能检索回答，能调用工具（读文件、创建任务、查日期），流式输出，工具调用过程可见，写操作需要用户确认。

必须具备：
- 后端：Node 服务，SSE 流式接口，SQLite 或 Postgres 持久化会话
- 前端：流式渲染、工具调用卡片、确认对话框
- Agent：手写循环，上下文管理，RAG 检索，多 Agent 协作（主 agent 派发子任务、结果回传），权限与危险命令拦截
- 评测：一组固定问题集，能比较两版 prompt 或检索策略的效果
- 工程：Docker 部署，README 含架构图、运行方式、取舍说明、评测结果

## 3. 学习模块

参考市场上 AI Agent 开发工程师培训的常见结构（如 [华测教育的 AI Agent 开发课程](https://www.huace-ai.com/course/ai-agent/)：模型应用基础 → 提示词与可靠输出 → 知识库与 RAG → Agent 与工具调用 → 工作流 → Skill/MCP → 评估与安全 → 部署交付），按能力模块组织。每个模块结束时都有一个可提交、可演示的阶段实践。

每个模块内的主题按设计文档的研究节奏推进：**撞墙**（在当前代码复现问题）→ **调研**（读开源实现，与 Claude Code、opencode、Aider 等对比）→ **设计**（结论写进学习记录）→ **实现**（合回主代码）。每个主题的学习记录都要有"与开源实现对比"一项，结论要落到一次提交上。

不再把每个 Day 绑定到固定周和日期。已完成的 Day 编号保持不变，后续按模块顺序编号。

每个模块结束时对照"出口标准"自检。不合格的部分在下一个模块前补齐，不跳过。

**补课规则（学习节奏不固定时使用）**：
- Day 编号是学习顺序，不是日期。缺课不影响编号，下一次直接接上未完成的 Day。
- 一次学 1–2 个 Day 是允许的。两天内容合并学习时，两个 Day 各自写一份学习记录，不合并成一条。
- 模块的出口标准未达成时，不进入下一个模块的"阶段实践"，但可以先学下一个模块的单个主题。
- 长时间中断后，先读 `LEARNING_LOG.md` 的"模块进度"和"下一步"，再开始新的 Day。


## 5. 风险与应对

- **时间不够**：优先保留 RAG、后端、评测、部署。MCP 与 LangGraph 可以缩减为演示，不删除。
- **某个模块卡住**：先写下问题，用一天时间找资料和开源实现对比，仍然卡住就记录在学习记录里，继续往下，不无限停留。
- **内容偏离**：每两周对照 2–3 个真实岗位的要求检查一次，必要时调整。
- **太多主题，难以形成闭环**：每个主题都要落到主线项目的一次提交上，没有提交的不算完成。
