# 面试题整理：模块一（Agent 核心）与模块二（RAG）

来源：公开的 Agent 面试题整理（xiaopangq 的《Agent 智能体开发面试题总结》、面灵AI 的 Agent 专项题单、BigKunLun 的 Agent-Interview-100），按本仓库 Day 1–14 的内容筛选并归类。题目后的"我们的对应"指本仓库中可以用来举例的代码或实验，面试时能结合项目回答会更有说服力。

## 一、模块一：Agent 核心（Day 1–10）

### 1. Agent 循环

**Q：Agent 和直接调用 LLM 有什么区别？**

直接调用是一次性生成；Agent 是"请求模型 → 执行工具 → 回传结果 → 再请求"的循环，直到模型不再调用工具。
我们的对应：[src/day06/agent.ts](../src/day06/agent.ts)

**Q：ReAct 是什么？优缺点是什么？**

Thought → Action → Observation 交替进行。优点是每一步可解释，并且能根据观察结果纠错；缺点是步数多、成本高，容易绕圈，需要设置步数上限和重复调用检测。

**Q：Agent 循环为什么必须设置最大步数？**

模型可能反复调用同一工具或陷入无效循环，不设上限会无限消耗 Token。超过上限时应停止并如实告知用户。
我们的对应：Day 5 的 `maxSteps`、Day 6 的循环上限

**Q：工具调用的完整链路是什么？**

模型返回 `tool_calls`，应用解析参数、校验、执行，再把结果以 `tool` 消息回传（`tool_call_id` 必须对应）。模型只生成参数，执行由应用代码完成。

### 2. Function Calling 与工具

**Q：Function Calling 的原理是什么？**

请求时附带工具描述（函数名 + JSON Schema）。模型判断是否需要调用，需要时输出结构化的函数名和参数，由应用执行。模型不会直接执行工具。
我们的对应：[src/day05/tools.ts](../src/day05/tools.ts)

**Q：工具很多时，模型如何选对工具？**

工具少时全部注入；工具多时先做意图分桶，只注入候选子集；相似工具可以合并成带 action 参数的通用工具；工具描述里写清使用场景和反例，能明显降低误选。

**Q：工具参数格式错误或工具执行失败怎么处理？**

先按 Schema 校验，失败时把错误作为 `tool` 消息回传，让模型修正参数重试，并限制次数。不能静默转换参数，也不能让模型编造工具结果。
我们的对应：Day 5 中参数错误显式报错

**Q：什么是工具幻觉？如何缓解？**

模型调用不存在的工具、编造参数，或者伪造工具结果。缓解方法：工具名白名单校验、参数按 Schema 校验、工具结果由系统真实执行后回传，并用 few-shot 示例展示"无法完成时怎么回答"。

### 3. 结构化输出

**Q：`json_object` 能保证输出正确吗？**

只保证输出是合法 JSON，不保证字段和类型正确。必须做 schema 校验，失败时把错误回传让模型修正，并限制重试次数。
我们的对应：[src/day04/extract.ts](../src/day04/extract.ts)，`validateTask` 与最多 3 次重试

**Q：如何解析模型返回的结构化结果？**

先去掉 Markdown 代码块标记，再提取 JSON 片段，然后做 Schema 校验和业务校验（枚举、范围、日期格式）。

### 4. 上下文管理

**Q：为什么上下文越长，成本和延迟越高？**

每一轮请求都要重新发送完整历史，输入 Token 随轮数增长。模型本身不保存历史，"记得"完全来自请求中的 messages。
我们的对应：Day 2 多轮对话与 Day 3 上下文管理

**Q：长对话的常见压缩方法有哪些？各有什么代价？**

- 滑动窗口：只保留最近 N 轮，简单但丢信息
- 摘要压缩：早期对话总结成摘要，省 Token 但丢细节，并多一次模型调用
- 预算触发：超过 Token 预算才压缩
- 混合：近期原文 + 远期摘要，通常最稳

我们的对应：Day 3 的"最近 2 轮原文 + 早期摘要"，Day 10 的 A/B/C 对比

**Q：压缩时为什么要按轮切分，而不是按消息条数？**

按条数切分会拆开 `tool_calls` 和对应的 `tool` 消息，导致 API 报错或历史残缺。
我们的对应：Day 6 的按轮压缩

**Q：工具执行中途失败，历史应该如何处理？**

整轮回滚，避免留下不完整的 `tool_calls`。
我们的对应：Day 6 中失败整轮回滚

### 5. 工具安全

**Q：Agent 的工具安全应该怎么设计？**

顺序为：校验 → 人工确认（高影响操作）→ 执行。具体包括白名单、参数检查、最小权限、沙箱或受限执行、审计日志。安全规则必须写在代码中，不能只靠 prompt 约束模型。
我们的对应：[src/day07/agent.ts](../src/day07/agent.ts)，白名单 + `execFile` + y/N 确认

**Q：`exec` 和 `execFile` 有什么区别？为什么影响安全？**

`exec` 把字符串交给 shell 解释，存在命令注入风险；`execFile` 直接传入参数数组，不经过 shell。

**Q：如何防止路径穿越？**

对路径做规范化后检查是否仍在允许目录内。注意符号链接问题，我们的实现目前不解析符号链接，这是已知的改进点。

**Q：什么是提示注入？如何防范？**

外部内容（网页、文档）中夹带的指令可能诱导模型调用工具。防范方法：外部内容用标签包裹并声明"仅作数据"，工具名和参数只信任系统指令区，高危操作必须人工确认。

### 6. 流式输出与工程化

**Q：流式输出怎么实现？**

设置 `stream: true`，逐块读取 `delta` 并拼接。Agent 场景中还可以推送结构化事件（思考、工具调用、工具结果、最终回答）。
我们的对应：[src/day02/chat.ts](../src/day02/chat.ts)

**Q：System prompt 为什么要分层？**

基础层（角色与身份）、规则层（安全与格式约束）、运行时层（当前日期、用户信息等）来源不同、变化频率不同，分开管理便于维护，并且每次请求重新拼接。
我们的对应：Day 8

**Q：如何保存和恢复会话？**

使用 JSONL 逐行追加消息，恢复时逐行读取重建 messages。JSONL 适合追加写入，单行损坏时影响范围也较小。
我们的对应：Day 9

## 二、模块二：RAG（Day 11–14）

### 7. RAG 的流程与动机

**Q：为什么需要 RAG？**

解决四类问题：知识过时、领域知识缺失、幻觉（有依据才回答）、知识更新无需重新训练。

**Q：简述 RAG 的离线与在线流程。**

- 离线：加载文档 → 切分 → 向量化 → 写入索引
- 在线：问题改写（可选）→ 问题向量化 → 检索 Top-K（可加关键词检索）→ 重排（可选）→ 拼入 Prompt 生成答案

我们的对应：Day 11（离线索引）、Day 12（在线问答）

**Q：RAG 和微调如何选择？**

RAG 管知识，更新快、可溯源；微调管风格、格式和能力。知识类问题用 RAG，输出格式或风格需要稳定时考虑微调，两者可以组合。

### 8. 切分与 Embedding

**Q：切分块大小如何影响效果？**

块太小会丢失上下文，块太大会混入无关内容并稀释相关性。我们的实验中，块大小 200 时 Recall@3 为 5/5，500 时为 3/5，1000 时为 4/5。
我们的对应：Day 11 的切分对比

**Q：Embedding 是什么？如何衡量相似度？**

Embedding 把文本映射为固定维度的向量，语义相近的文本距离近。常用余弦相似度，关注方向而不关注长度。
我们的对应：Day 11 的本地向量检索

**Q：向量数据库如何选型？**

数据量小且已有 PostgreSQL 时用 pgvector；数据量大用 Milvus；希望全托管用 Pinecone；已有 Elasticsearch 栈时可以直接使用它的 dense_vector。选型还要看是否需要混合检索和过滤。

### 9. 检索与混合检索

**Q：为什么纯向量检索不够？**

向量检索擅长语义相似，但对人名、型号、编号、低频专有词等精确匹配效果差。
我们的对应：Day 14 中 BM25 命中"提交格式"类问题，向量检索未命中

**Q：BM25 的原理是什么？**

基于词频（TF）和逆文档频率（IDF），并对文档长度做归一化。词越稀有、在文档中出现越多，得分越高。关键参数 k1 控制词频饱和速度，b 控制长度归一化强度。
我们的对应：[src/day14/bm25.ts](../src/day14/bm25.ts)，K1 = 1.5，B = 0.75

**Q：RRF（Reciprocal Rank Fusion）是什么？为什么要用它融合？**

对每一路检索结果按排名计算 $\frac{1}{k + rank}$，然后相加，常用 $k = 60$。RRF 融合的是排名，不是分数，因此不需要统一 BM25 分数与余弦相似度的量纲。
我们的对应：[src/day14/hybrid.ts](../src/day14/hybrid.ts)

**Q：混合检索一定比单一检索好吗？**

不一定。我们的实验中，向量、BM25、RRF 的 Recall@3 都是 3/5，融合不保证命中数增加，需要用评测集验证。

### 10. 重排（Rerank）

**Q：Rerank 是什么？为什么要做？**

粗召回追求速度，结果中常混入无关片段。Rerank 用更精细的模型（如交叉编码器）对候选逐一打分重排，精度高但延迟也高，因此只对粗召回的 Top-N 执行。
我们的对应：[src/day14/rerank.ts](../src/day14/rerank.ts)，用 LLM 对 RRF 的前 10 条打分

**Q：Rerank 的局限是什么？**

只能重排候选池中已有的结果，池外的正确答案无法被找回。因此需要保证召回阶段的候选池足够大。

**Q：Cross-Encoder 和 Bi-Encoder 有什么区别？**

Bi-Encoder 分别编码问题和文档，再计算向量相似度，速度快，可预先建索引；Cross-Encoder 把问题和文档拼在一起编码，精度更高，但每个候选都要计算一次，无法预建索引。

### 11. 回答、拒答与评估

**Q：如何让 RAG 回答带引用，并在无依据时拒答？**

在 Prompt 中要求只根据给定材料回答，每个结论标注来源编号；检索结果与问题不相关时，要求模型明确说明"资料中没有依据"。
我们的对应：Day 12 的带引用问答与拒答

**Q：RAG 如何评估？**

- 检索质量：Recall@K（正确片段是否在召回结果中）、MRR（第一个正确结果的排名）
- 生成质量：忠实度（答案是否基于检索内容）、答案相关性
- 工程做法：建立 Golden Set，改切分或检索策略后做回归测试

我们的对应：Day 13 的 Recall@K 与引用正确率评估

**Q：误拒和正确拒答分别指什么？为什么要同时看？**

误拒是有依据的问题被拒答，正确拒答是无依据的问题被正确拒绝。只看拒答率无法区分"该答没答"和"不该答却答了"，需要两个指标一起看。
我们的对应：Day 13 的"有依据误拒"与"无依据正确拒答"

- 能回答"你项目里具体怎么做的"，并给出实际数字，例如 Day 11 的 Recall 对比、Day 13 的评估结果
