# Day 15 面试题：Node HTTP 服务基础与异步 I/O

对应代码：[src/day15/server.ts](../src/day15/server.ts)

**1. Node 是单线程的，为什么还能同时处理多个请求？单线程有什么风险？**
参考答案：JS 业务代码运行在单线程中，但 I/O 操作（网络、文件、DNS）由底层 libuv 通过操作系统的多路复用机制（Linux 的 epoll、macOS 的 kqueue）或线程池处理。发起 I/O 后，JS 线程注册回调并立即返回，可以继续处理其他请求；数据就绪后事件循环再执行回调。风险在于 CPU 密集操作（大 JSON 同步解析、同步的 `readFileSync`、本地计算 embedding）会占住线程，阻塞事件循环，导致所有请求排队。Agent 调用大模型属于网络 I/O，适合这种模型，但本地计算要拆分或放到 worker 线程。

**2. HTTP 请求体为什么要通过 `data` 和 `end` 事件读取？直接 `JSON.parse(chunk)` 会有什么问题？**
参考答案：body 是以 stream 形式分块到达的，块的大小由网络决定，不一定与消息边界对齐。`end` 事件表示全部数据到齐，此时才能完整解析。若对每个 chunk 单独解析，不完整的 JSON 会抛出 `SyntaxError`；而且在事件回调中抛出的异常不会被 `createServer` 的 `try/catch` 捕获，会导致进程退出。合法但被切断的片段还可能被错误解析（如 `1234` 切成 `12` 和 `34`）。正确做法是先拼接，`end` 后统一解析。

**3. 为什么 `Content-Length` 必须用字节数而不是字符数？`setEncoding('utf8')` 解决的是什么问题？**
参考答案：HTTP 协议中的长度按字节计算。JavaScript 字符串的 `length` 是 UTF-16 码元数，中文等字符在 UTF-8 下占 3 个字节，用字符数会导致长度错误，客户端读取不完整或多读。`Buffer.byteLength` 按 UTF-8 编码后的字节数计算。`setEncoding('utf8')` 则让 stream 在内部处理跨 chunk 的多字节字符，避免一个汉字的字节被切到两块后分别解码出现乱码。

**4. 常见的状态码 400、404、415、500 分别表示什么？这些场景中为什么要先检查 `Content-Type` 再读取 body？**
参考答案：400 表示客户端请求格式错误（如 JSON 解析失败）；404 表示路径不存在；415 表示服务端不支持请求的媒体类型；500 表示服务端内部错误。先检查 `Content-Type` 可以在读取 body 之前拒绝不支持的格式，避免浪费资源读取无用数据，也让错误原因更明确。500 需要配合 `try/catch` 使用，并注意 `res.headersSent` 已为 true 时不能再写响应头。

**5. 如果服务端某个接口需要调用大模型并耗时 30 秒，会对其他接口产生什么影响？应如何设计？**
参考答案：只要该请求在 `await` 等待的是 I/O，事件循环不会被占用，其他接口仍能正常响应，Day 15 的并发测试已验证这一点。但需要注意：长耗时请求会占用连接和内存，客户端可能超时。设计上应设置超时（如 `AbortSignal.timeout`）、限制并发数量、对长任务考虑异步化（先返回任务 ID，再轮询或通过 SSE 推送结果），并避免在请求路径中做 CPU 密集计算。
