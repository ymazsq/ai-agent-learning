# Day 10 面试题：上下文压缩策略对比

对应代码：[src/day10/agent.ts](../src/day10/agent.ts)

**1. 滑动窗口为什么会丢掉早期的关键事实？怎样缓解？**
参考答案：窗口只保留最近几轮，早期消息直接从请求里移除，模型就没有机会再看到它们。缓解方式有三种：把关键事实固定放进 system prompt 或单独的"记忆"字段；窗口之外保留摘要；或者用检索从历史里按需取回。窗口本身只适合不需要长期记忆的场景。

**2. 每轮都做摘要有什么代价？摘要为什么也会丢信息？**
参考答案：每次摘要都要额外调用一次模型，延迟和 token 成本都增加，并且随轮数线性增长。摘要是模型的有损改写，模型可能省略它认为不重要、但后面需要的细节（比如代号、数字、路径）。所以摘要适合保留结论，不适合保留精确值。

**3. 为什么要先截断旧的工具结果，再考虑摘要？**
参考答案：工具结果通常很长，但大部分内容在之后的轮次里已经没有用，截断几乎不花额外的模型调用。摘要则要花一次调用，还可能丢失细节。这个做法的前提是：截断的内容不能是后续还需要引用的原始数据，并且要在结果里标记被截断，让模型知道这里有缺失。

**4. 怎样选择 token 预算？预算应该按什么来设？**
参考答案：预算应该根据模型的上下文窗口、单次输出的预留空间和成本目标来设，留出安全余量。触发条件应该看实际请求的大小（用接口返回的 `usage.prompt_tokens` 或 tokenizer 估算），而不是轮数，因为一轮里工具输出的大小差别很大。预算过低会频繁压缩、增加调用，过高则起不到保护作用。

**5. 怎样证明一种压缩策略真的有效？只看 token 数够吗？**
参考答案：不够。需要同时看三件事：token 用量（峰值和合计）、调用次数（尤其是额外的摘要调用）、以及任务是否完成（比如早期事实能否在后面被正确使用）。还要多次运行，因为模型输出有随机性，单次结果不能说明问题。好的评测应该设计一个"后面必须用到早期信息"的任务，否则窗口和摘要的差异体现不出来。
