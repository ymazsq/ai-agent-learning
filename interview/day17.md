# Day 17 面试题：SQLite 持久化与基础鉴权

对应代码：[src/day17/app.ts](../src/day17/app.ts)

**1. 内存中的会话数据和写入 SQLite 的数据，在进程重启后有什么区别？Agent 为什么需要持久化会话？**
参考答案：进程内的 `Map` 或数组随进程退出而丢失，重启后用户的对话历史、已登录状态全部消失。写入 SQLite 文件后，数据保存在磁盘上，重启后可以按 `user_id` 或 `token` 查回。Agent 的会话往往跨越多次请求甚至多天，如果不持久化，用户刷新页面或服务重启后就无法继续上下文，因此需要把消息历史和运行状态落库。

**2. 为什么密码不能明文存储？`scrypt` 相比直接 SHA-256 有什么优势？**
参考答案：明文存储一旦数据库泄露，所有账号都暴露，还可能影响用户在其他站点的密码。直接用 SHA-256 计算速度快，攻击者可以用 GPU 高速枚举。`scrypt` 是内存困难型（memory-hard）的密钥派生函数，每次计算需要大量内存，攻击成本高。每个用户还要使用随机 salt，避免相同密码得到相同哈希，抵御彩虹表攻击。校验时应使用 `timingSafeEqual` 做常量时间比较，防止时序攻击。

**3. 一个 Bearer token 鉴权的完整流程是什么？服务端如何判断请求无权限？**
参考答案：客户端用用户名和密码调用登录接口，服务端校验通过后生成随机 token，保存到 `tokens` 表并返回给客户端。之后客户端在请求头 `Authorization: Bearer <token>` 中携带 token。服务端收到请求后解析头部，到表中查找 token 对应的用户，找不到则返回 401。登录失败、缺少头部、token 无效都应返回 401，而不是 403；403 表示身份已确认但没有权限。

**4. 为什么 token 要用随机数生成，而不是直接用用户 ID 或用户名？token 泄露后应该怎么办？**
参考答案：用户 ID 是可以预测的，攻击者可以伪造请求头。随机 token（如 `randomBytes(32)`）不可猜测。token 泄露后，服务端应能撤销它，即删除 `tokens` 表中对应的记录，并要求用户重新登录。生产环境中还应设置过期时间，并通过 HTTPS 传输，避免明文被截获。

**5. 为什么 SQLite 的 `better-sqlite3` 需要原生编译？在 pnpm 10 中有什么额外步骤？**
参考答案：`better-sqlite3` 是 C++ 原生模块，需要为当前 Node 版本和平台提供二进制文件。pnpm 10 默认不执行依赖的安装脚本以提高安全性，因此需要在 `package.json` 的 `pnpm.onlyBuiltDependencies` 中显式允许 `better-sqlite3`，否则运行时会因找不到绑定而报错。Node 20 不包含内置的 `node:sqlite`（需要 22.5 以上），所以本例选用 `better-sqlite3`，并固定到支持 Node 20 的 11.x 版本。
