# Day 9 面试题：会话持久化与恢复（JSONL）

对应代码：[src/day09/agent.ts](../src/day09/agent.ts)

**1. 为什么用追加写入的 JSONL，而不是每轮结束后整体重写一个 JSON 文件？**
参考答案：追加写入每条记录只写一行，崩溃时最多丢失最后一行，前面的历史都完整。整体重写要先截断文件再写入，中途崩溃会留下半个 JSON，整个会话都无法解析。另外 JSONL 便于逐行读取、检查和追加压缩或回退记录，不需要读取整个文件再改写。

**2. 恢复时怎样判断最后一轮是未完成的？为什么不能直接保留？**
参考答案：看最后一条用户消息之后的内容。如果最后是一条没有 `tool_calls` 的 assistant 消息，说明这一轮正常结束；否则就是未完成（比如只有工具调用、没有最终回答，或者只有用户消息）。不能直接保留，因为下一次请求会带着残缺的上下文，模型可能重复执行工具，或者基于不完整的结果继续推理。Day 9 的做法是截掉这一轮，并追加一条 `rollback` 记录，让文件和内存状态保持一致。

**3. 压缩后的摘要为什么要记录 `cut`？如果只记录摘要文本，恢复时会出什么问题？**
参考答案：`cut` 表示摘要覆盖了前面多少条消息，恢复时需要用同样的位置截掉已被摘要的消息。只记录文本的话，恢复时要么把被摘要的原始消息也放回历史（上下文重复、超出预算），要么无法判断哪些消息已经不需要保留。重放时的规则必须和运行时完全一致，否则恢复出来的历史会和崩溃前不同。

**4. 回退（rollback）为什么要写成一条记录，而不是直接改写文件？**
参考答案：追加记录保留了完整的操作历史，重放时按顺序执行就能得到同样的结果，文件仍然是追加式的，不需要特殊的修改逻辑。直接改写文件会丢失被回退的内容，也容易在改写过程中出错。这和数据库的 WAL（预写日志）或事件溯源是同一思路。

**5. 设计会话持久化时，哪些内容应该存，哪些不应该存？**
参考答案：应该存能用于重放的消息、压缩摘要和回退记录，这些是恢复状态所需的最小信息。不应该存 API Key、临时派生数据（比如每次请求重新生成的运行时 system prompt），也不应该把完整的模型响应元数据当作恢复依据。存的内容要保证"按顺序重放就能得到同样的历史"，同时避免把敏感信息写进文件。
