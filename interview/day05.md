# Day 5 面试题：Function Calling

对应代码：[src/day05/tools.ts](../src/day05/tools.ts)

**1. 描述一次完整的 Function Calling 流程。**
参考答案：应用把工具的名称、描述和参数 JSON Schema 随请求发给模型。模型判断需要时，返回 `tool_calls`（工具名和 JSON 格式的参数），而不是普通文本。应用解析参数、在本地执行函数，再把结果以 `role: 'tool'` 消息（带上对应的 `tool_call_id`）追加到 messages，再次请求模型。模型据此继续推理，直到不再返回 `tool_calls`，给出最终回答。

**2. 模型是怎么"调用"工具的？谁真正执行了代码？**
参考答案：模型只生成工具名和参数，并不执行任何代码。执行的是应用程序。这一点很重要：工具的安全性、权限校验、超时和错误处理都要由应用负责，不能依赖模型的判断。

**3. 为什么要把 assistant 的 tool_calls 消息原样放回 messages？**
参考答案：每条 `tool` 消息都要通过 `tool_call_id` 对应到 assistant 消息里的某个调用。如果 assistant 消息丢失，模型就看不到自己发起过哪些调用，接口通常会报错，或者模型无法正确理解工具结果。

**4. Agent 循环为什么要设置最大步数？**
参考答案：模型可能陷入反复调用同一工具的循环，比如工具总是返回错误而模型不断重试。不设上限会导致无限循环、费用和延迟失控。通常还要配合超时和重复调用检测。

**5. 工具参数校验失败时应该怎么处理？**
参考答案：模型生成的参数不可信，应用必须校验。校验失败时，不应静默修正，也不应直接崩溃，而是把错误信息作为 `tool` 消息回传，让模型修正参数后重试，同 Day 4 的结构化输出思路一致。

**6. Function Calling 和结构化输出有什么区别？**
参考答案：结构化输出解决"最终回复长什么样"，应用拿到 JSON 后直接使用。Function Calling 解决"模型要不要、以及如何调用外部能力"，模型在对话过程中多次决策，应用负责执行并把结果回传。Function Calling 是 Agent 的基础，结构化输出是其中参数生成的一种形式。
